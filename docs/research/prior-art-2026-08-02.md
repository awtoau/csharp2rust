# Fresh prior-art sweep, 2026-08-02

Second pass, excluding everything already in `prior-art.md` and siblings
(c2rust, c2rust-analyze, Corrode, IL2CPP, J2K, pyrs/MonkeyType, VERT, FLOURINE,
safe-gc, rust-gc, Bun). Every finding was verified by reading the paper text or
the repository, never the abstract or README.

## The four that would change next week

### 1. Mutate the C# INPUT — a published translator-adequacy metric we do not have

*Mutation analysis for evaluating code translation*, Guizzo, Zhang, Sarro,
Treude, Harman (UCL/Meta), **Empirical Software Engineering 29:19 (2024)**,
open access. https://link.springer.com/article/10.1007/s10664-023-10385-w

Defines **MBTA** and **MTS**:

> "MBTA is novel in the sense that mutants are compared to **their translated
> counterparts**, and not to their original program's translation."

Mutate the *source*, translate the mutant, check the mutant against *its own*
translation. On 612 Java–Python pairs and 75,082 mutants against TransCoder and
j2py: **70.44% and 70.64% of mutants are incorrectly translated.** And:

> "we have also observed interesting scenarios in which the translators
> successfully translated the original program, but it failed to generate
> correct translations for any of its mutants, thus suggesting **overfitting in
> the translation procedure**."

**Why this matters here.** This project mutates the *output*, which measures the
ORACLE's sensitivity. MBTA mutates the *input* and measures the TRANSLATOR's
adequacy. Two different instruments; we own one. A converter that is correct on
a peripheral but wrong on that peripheral with one operator flipped is
overfitted — which is "a rule that only ever matches one site", made
**measurable** rather than argued.

**Cost: lower for us than for anyone.** We already have the corpus DB, a
converter that reads only from it, and a trace oracle. Add C# mutation operators
over the ingested `IOperation` tree — flip `ConditionalOr`/`ConditionalAnd`,
off-by-one a shift width, swap a comparison, delete a statement — then
re-ingest, re-emit, re-replay. Survivors are equivalent mutants or holes.

Caveat the paper is explicit about: equivalent mutants are an unsolved confound.
Treat MTS as a trend, like instances-per-rule.

### 2. A published ablation says this architecture is worth 73 points, and LLM-only is ZERO

*Scalable, Validated Code Translation of Entire Projects using LLMs*, Zhang,
David, Wang (Bristol), Paulsen, Kroening (AWS). **PLDI 2025**,
doi:10.1145/3729315. Tool: **Oxidizer**. Go→Rust, 7 real projects, 369 functions.

| configuration | % compiled | % I/O-equivalent |
|---|---|---|
| full (feature-mapping rules + type-compat checks) | 99 | **73** |
| no type-compatibility check | 98 | 61 |
| **no feature mapping — LLM + repair only** | 27 | **0** |

Zero. The pipeline aborts on all seven benchmarks without predefined rules.
This is the strongest published reply to "rule-based methods suffer from limited
coverage", and it comes from the LLM side of the field.

**The stealable idea, and it is the best thing in this sweep: a rule is a
judgment with a check on the OUTPUT, not just a match on the input.** Their
rules are inference rules whose conclusion carries `code ⇓ <expected target
shape>` — a *static check that the emitted Rust has the required shape*.
Failure rejects and re-queries; no oracle needed.

Our `rule` table has a match-shape and `rule_negative`, and **no emit-shape
postcondition**. That is a schema field plus an emitter hook, and it is the
mechanism that would have caught the invented `.with_reserved(9, 23)`.

Two smaller transfers: they picked ONE error type (`anyhow::Error`) universally,
because per-site model-chosen error types produce code that "looks idiomatic"
and does not compile — uniformity is doing work independent of which mechanism
D4 settles on. And functions with no test coverage count as NOT equivalent, so
their 73% is deflated by design. That is the honest version of "coverage means
validated".

### 3. Microsoft's C#→Rust maps are the best public ones, and both stop where our hard problem starts

- **microsoft/rust-for-dotnet-devs** — 403★, active. Pages for exception
  handling, nullability, structs, records, equality, operator overloading,
  generics, conversion, LINQ, memory management, threading, async.
- **microsoft/RustTraining** — 14,761★, created 2026-03-13. Contains a
  `csharp-book/` of 17 chapters.

**Verified, verdict mixed.** The LINQ, exception-handling and struct pages are
substantive and would seed `csharp_core.json` directly. But
`rust-for-dotnet-devs/inheritance.md` is **ten lines** ("use traits and
supertraits") and `polymorphism.md` is seventeen. RustTraining's inheritance
chapter is 257 lines of canonical `Animal`/`Dog` and never addresses shared base
*state* across a deep hierarchy — the actual open decision.

Worth: a licence-clean seed of *generic* mappings at near-zero cost, and a
citable Microsoft-authored corroboration that the inheritance question has no
off-the-shelf answer. Tutorial-grade, so candidates only — three validated
instances still required.

Caveat: RustTraining gained 14,761 stars in under five months and its prose
reads as substantially model-generated. Candidate list only.

### 4. A working, MIT-licensed C# IR for exception regions — and it names the trap in D4

**dubiousconst282/DistIL** — 156★, MIT, post-build IL optimiser with its own SSA
IR, doing the full round trip CIL exception clauses → structured IR → CIL.
`GuardInst` (catch/filter/finally/fault), `LeaveInst`, `ResumeInst`, `ThrowInst`.

Two transfers, both load-bearing:

- **The leave-chain.** Exiting nested protected regions requires a *chain* of
  intermediate blocks, one per boundary crossed, so each intervening `finally`
  runs in order. **Any translation mapping `catch` onto a single early-return
  construct — `?`, a `Result` bubble, a one-level unwind — gets multi-level
  exits wrong SILENTLY, because the one-level case passes.** That is a concrete
  negative test that can be written today.
- **Variables crossing a region boundary cannot be SSA-promoted.** DistIL marks
  them `CrossesRegions` and materialises them as exposed local slots. Any IR
  built over `try` bodies inherits this, and discovering it afterwards is
  expensive.

Read-only design reference, not a dependency.

## Verification — the richest section

### Kaizen: perfect compilation with zero correctness, measured

*Kaizen: Metamorphic Fuzzing and Differential Testing for LLM-Translated Code*,
arXiv 2607.04058 (2026). CUDA→OpenMP, 16 applications.

| application | compilability | correctness |
|---|---|---|
| `lif` | **393/393 = 1.00** | **0/393 = 0.00** |
| `winograd` | 0.94 | 0.00 |
| `flip` | 0.99 | 0.00 |
| `dense-embedding` | 0.98 | 1.00 |

> "The results reveal a **bimodal pattern**: some applications achieve
> near-perfect correctness while others with equally high compilability achieve
> zero correctness, confirming that shallow evaluation proxies create false
> confidence in translation quality."

This is our defect class with a number on it.

**The warning attached is the reason to read it.** Their fuzzer found bugs in
the developer-written CUDA *reference*. Here, aggressive trace fuzzing will
surface Renode's own defects — and CLAUDE.md says reproduce known Renode defects
faithfully first, so a divergence there is a **pass**, not a failure. Any
fuzzing tooling must be able to say which.

### Lost in Translation — a bug taxonomy, and rule-based beating LLMs by 34 points

ICSE 2024, doi:10.1145/3597503.3639226. 1,700 samples, 43K+ translations, 1,748
manually labelled bugs, ~630 person-hours.

- Correct translations range **2.1% to 47.3%** across seven LLMs.
- **C→Rust: C2Rust 95% vs GPT-4 61%.** C2Rust's 5% failures were compilation
  errors, mostly unused imports.
- **Java→C#: JavaToCSharp 0%** — nothing it produced compiled.

**Do not quote their 13.4% functional-error figure as our number.** Their
"success" means passing the benchmark's tests, so the 13.4% are bugs their tests
DID catch. The class we fear — behaviourally inert wrong code no test
distinguishes — is invisible to their methodology by construction and is **not
measured anywhere in the paper**. It is the most quotable and most misleading
number in the literature.

### CRUST-Bench — repo-level C→safe-Rust, and two findings that bite

COLM 2025. 100 C repos with hand-written safe-Rust interfaces and tests.
Best model (o3): 35/19 pass@1 build/test, 63/48 after three test-repair rounds.

- **Adding failing-test information to a repair loop LOWERS build success by
  5–20 points** while raising test pass by 0–9. Test feedback "encourages the
  model to make more aggressive semantic changes". Directly relevant if trace
  failures are ever wired into a repair loop: the two feedback channels fight.
- **`unimplemented!()` is the dominant residual error class**, reaching 44–46%
  of projects even after repair. That is the LLM's version of a hand-written
  stand-in that looks finished. **`check_generated.py` should treat `todo!()`
  and `unimplemented!()` in generated output as a recorded gap, never as
  output.**

### Google at industrial scale — deterministic first, LLM for the residue

FSE 2025 industry, doi:10.1145/3696630.3728542. 39 migrations, 93,574 edits.

Architecture is ours: static categorizers identify what can be changed
deterministically "with 100% confidence" and do it; only the residue reaches the
LLM. 74.45% of changes LLM-generated, 25.55% human-only.

**Stealable metric: LLMΔ vs HumanΔ by Levenshtein per file** — a *continuous*
version of our binary patch count, which distinguishes a rule that is 80% right
from one that is 5% right. Our scorecard currently cannot.

Do NOT cite their "50% time reduction": the paper says outright *"We do not have
concrete wall-clock effort."*

### LLMigrate — a measured scaling law for omission

arXiv 2503.23791. **GPT-4o omits code in 1.67% of short functions but 47.41% of
long ones.**

This cuts slightly against the cluster-invocation rule, which is a *cost*
argument. There is also a *correctness* argument for small units, and clusters
can be large. Cheap mitigation: count emitted-vs-expected members per cluster
response and fail rule induction if members were silently dropped.

## Constructs

- **`yield return`**: Rust `gen` blocks are **still unstable** (rust-lang#117078
  open, updated 2026-07-17), so emitting `gen` is not an option for a
  stable-toolchain deliverable. The option nobody writes up is an explicit
  state-machine struct implementing `Iterator` — **which is what the C# compiler
  itself does**. Note it lowers *below* `IOperation`, so the walker sees
  `yield return` unlowered and the emitter must build the machine itself: a
  whole-method rewrite, not a rule.
- **Exception filters** (`catch (E e) when (cond)`): the filter runs *before*
  unwinding, so side effects observe the pre-unwind stack. Not reproducible by a
  `Result` bubble or a caught panic, and **nobody has published how to do it.**
  Check whether the cut contains any before spending on it.
- **Runtime helpers over rules**: `ccxt/ast-transpiler` (TS → 6 languages
  including Rust) puts language mappings in DATA — a fifth independent arrival
  at the `rulesdb` boundary — and solves "the target cannot express the source's
  semantics" with a shipped runtime helper library. Read for us: put C#
  semantics Rust lacks (checked/unchecked arithmetic, boxing, multicast delegate
  lists, `IDisposable` ordering) in `csharp-rt` and let rules emit *calls*.
  `rt::checked_add(a, b)` is reviewable and testable once; inlined overflow
  semantics at every site is not.
- **GC**: *Alloy* (OOPSLA 2025, doi:10.1145/3763179) is the newest work, but is
  implemented as **a fork of rustc** — prohibitive. What is free is its
  finalizer-safety analysis: C# finalizers and `IDisposable`/`using` have exactly
  the "is it safe to run this destructor here, and is it too early?" problem, and
  this is the only place it is analysed rather than assumed.

## Two other `IOperation` transpilers, both instructive

- **Sergio0694/ComputeSharp** — production C# → HLSL, Roslyn rewriter over
  `IOperation`. 3,152★, MIT, active.
- **SmolIndieGame/CSharp-To-MLog** — the only other `IOperation`-driven
  transpiler found. **Dead since 2023, one star.** It independently split into
  `OperationParsers/` (per `OperationKind`) and `InvocationParsers/` (per target
  API) — CLAUDE.md's language-mapping-vs-project-idiom split, arrived at
  independently. It covers ~15 operation kinds before stopping: a datum on how
  far a hand-written `IOperation` transpiler gets when the mappings live in code
  instead of data.

## Uncertainty

- `grep.app` answered `curl` with a bot checkpoint and was not swept; SearchCode
  likewise. Marginal value judged low given GitHub code search returned four
  files for the decisive query, but it is a hole.
- Kaizen is very recent and has no venue found. Preprint-quality numbers; the
  *method* is standard metamorphic testing and does not depend on acceptance.
- The Oxidizer ablation is seven Go projects, not a benchmark suite. The "0%
  without rules" result rests on their pipeline aborting, which is a property of
  their pipeline as much as of LLMs. Strong evidence, not proof; the compilation
  column (27% vs 99%) is the conservative version.
